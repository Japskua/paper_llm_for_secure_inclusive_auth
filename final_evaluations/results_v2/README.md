# results_v2 — repeated-runs evaluation data (2026)

Standalone guide to this directory. Everything needed to understand, verify or
re-analyse the data is here; no other document is required.

**This is not a revision of `../results/`.** That directory holds the original
2025 single-run evaluation (3 artifacts, 5 judges, 30 result files, entered by
hand). This directory holds a separate, larger experiment: **2 user stories × 3
cases × 10 independent runs = 60 artifacts, each scored by 7 judges on 2 tracks,
3 times over — 2,457 judgements and 36,855 individual item scores**, all
collected programmatically. The two directories share no data.

---

## 1. What the experiment is

Does asking an LLM to make code accessible to a user with a cognitive condition
degrade its security?

Each study fixes the security requirements and varies **only** the inclusivity
specification across three cases:

| Case | Inclusivity specification |
|------|---------------------------|
| 1 | None. Functional goal and security requirements only. |
| 2 | Condition named, nothing more (`"cognitive condition ADHD"` / `"dyslexia"`). |
| 3 | Detailed: description of the condition plus concrete inclusivity requirements. |

Two studies, deliberately parallel so neither can be dismissed as stylistically
different from the other:

| Study | Software | Cognitive condition | Directory |
|-------|----------|--------------------|-----------|
| 1 | Password recovery, health portal | ADHD | `password_recovery_health/` |
| 2 | MFA enrolment, online banking | Dyslexia | `mfa_enrolment_banking/` |

Artifacts were generated by `openai/gpt-5.6-terra` (snapshot `-20260709`) through
a three-agent pipeline (Tasker → Coder → Evaluator, max 12 iterations), one
single-file Bun application per run. **No seed is set anywhere**: a fixed seed
would suppress the between-run variance the repeated-runs design exists to
measure. Frontier reasoning models no longer expose `temperature`, so
`reasoning_effort` is pinned to `medium` and recorded per run instead.

Routing is pinned to the model's own provider with fallbacks disabled, and each
run records the dated snapshot the provider actually served
(`model_versions` in `batch_manifest.json`) rather than only the alias asked for.

Two judgements cannot collide, because no two share a path.

### Where the scored artifacts live

This directory holds only the *judgements*. The artifacts themselves are in
`../../generations/<study>/<case>/<run>/`, using the same case and run names:

| File | Contents |
|------|----------|
| `app.ts` | the artifact — this is what the security judges scored |
| `screenshots/` | the images the inclusivity judges scored, in order |
| `code_iter*.tsx`, `tasker_report_iter*.md`, `evaluator_report_iter*.md` | every generation iteration, kept |
| `log.jsonl`, `state.jsonl`, `console.log`, `tokens_summary.json` | full generation trace and token/cost accounting |
| `smoke.json` | did it boot, did it serve, `client_ok` and `page_errors` |
| `flow.json`, `flow_spec.json` | LLM-derived HTTP flow test and its result |
| `capture.json` | the screenshot walkthrough that was actually executed |
| `PASS_MARKER` | present when the Evaluator agent accepted the artifact |

Two study-level files sit above the cases: `batch_manifest.json` (model,
`reasoning_effort`, `seed`, `max_iters`, per-run outcome and cost) and
`capture_summary.json` (screenshot counts and complete/partial/failed per run).
`app_ts_sha256` in every judgement record ties back to the `app.ts` in this tree.

## 3. The judge panel

Seven models, one per lab, each verified before use to accept image input and
return parseable structured scores. Machine-readable roster, including rejected
candidates and reasons, in `../judge_panel.json`.

| Judge | Lab | Role vs the 2025 panel |
|-------|-----|------------------------|
| `openai/gpt-5.6-sol` | OpenAI | succeeds GPT-5 — **generator's own lab, see §7** |
| `anthropic/claude-opus-5` | Anthropic | succeeds Claude Sonnet 4.5 |
| `google/gemini-3.6-flash` | Google | succeeds Gemini 2.5 Pro |
| `mistralai/mistral-medium-3-5` | Mistral | succeeds Mistral Medium 3.1 |
| `x-ai/grok-4.5` | xAI | replaces DeepSeek 3.2 |
| `qwen/qwen3.8-max` | Alibaba | added |
| `moonshotai/kimi-k3` | Moonshot AI | added |

**Why the panel changed from 2025.** DeepSeek is now text-only and cannot score
a screenshot-based rubric; keeping it would give 7 security judges and 6
inclusivity judges. Google has no stable Gemini 3.x Pro — the only options were a
preview id (withdrawn eventually, breaking reproduction) or a moving alias — so a
current-generation flash was chosen over a previous-generation pro. Two judges
were added purely to tighten inter-rater reliability. `meta/muse-spark-1.1` was
selected and then dropped: it is geo-restricted to the United States.

**Provider caps.** Mistral rejects requests carrying more than 8 images. Where an
artifact has more screenshots, that judge receives 8 sampled evenly across the
journey, always keeping the first and last, so the whole arc is represented at
lower density rather than the tail being dropped. Affected records carry
`screenshots_sampled: true` and `screenshots_available`.

## 4. What each judge received

| Track | Payload |
|-------|---------|
| security | the artifact's `app.ts` source |
| inclusivity | that run's screenshots, in order, as images |

Each artifact is scored with the rubric **for its own case**, taken verbatim from
`../evaluation_rubrics/`. Study 2's rubrics live in the
`mfa_enrolment_banking/` subdirectory there; study 1's are at the top level.

Every record stores the SHA-256 of both the rubric used and the `app.ts` scored,
and the artifact hash is checked against the generation manifest **before** any
API call. An artifact that does not match is refused rather than scored.

### The scoring protocol

The rubric text is used unchanged, but a scoring protocol is appended:

1. **Judge each statement literally** — 5 means "I strongly agree this statement
   is TRUE of this system", including where the statement describes a weakness.
2. **Give a one-sentence justification per item**, stored in the record.
3. Reply as an object keyed `"1"`–`"15"`, validated to exactly fifteen integers
   in 1–5. A short, reordered or non-numeric reply is retried, never padded.

**Why.** Security items 2 and 3 are worded so that agreeing means the system is
*less* secure ("The same reset code works for any other user"). In the 2025
results the panel split 1-vs-5 on exactly those two items for the same artifact:
four judges answered literally, one evaluatively. That is interpretation noise,
and it halves the A01 construct. The justifications make any residual mis-reading
auditable.

## 5. Items, constructs and reverse coding

Both rubrics have 15 items, grouped into 5 constructs of 3.

**Security — identical in both studies, therefore comparable across them:**

| Construct | Items |
|-----------|-------|
| A01:2021 Broken Access Control | 1–3 |
| A02:2021 Cryptographic Failures | 4–6 |
| A03:2021 Injection | 7–9 |
| A05:2021 Security Misconfiguration | 10–12 |
| A07:2021 Identification and Authentication Failures | 13–15 |

**Inclusivity — NOT comparable across studies.** The item ranges match, but the
studies target different cognitive conditions and their rubrics name different
dimensions:

| Items | Study 1 (ADHD) | Study 2 (dyslexia) |
|-------|----------------|--------------------|
| 1–3 | attention | readability |
| 4–6 | memory | reading_load |
| 7–9 | comprehension | transcription |
| 10–12 | decision_making | orientation |
| 13–15 | learning | recovery |

> **Compare inclusivity only at the overall-score level between studies.**
> Construct-level inclusivity comparison across the two is meaningless.

**Reverse coding.** Security items **2 and 3** are reverse-worded in both studies
and are inverted (`6 − x`) before aggregation. Inclusivity has none. The rule is
identical across studies by design, so the constructs stay comparable. `raw_score`
and `adjusted_score` are both stored so the inversion is visible.

## 6. How the numbers are computed

Aggregation order, fixed before any result was seen:

```
item score (1–5, reverse-coded where applicable)
  → construct        mean of its 3 items
  → judgement        mean of the 5 constructs          → "overall"
  → judge            mean over that judge's 3 repeats
  → artifact         MEDIAN over the judges            → "artifact_score"
  → case             mean ± SD over the 10 artifacts
```

The **artifact** is the unit of analysis, giving **n = 10 per case**. The tests
therefore do not treat 2,457 judgements as independent observations when they are
seven opinions about sixty things. The median across judges is used rather than
the mean so one atypical judge cannot move an artifact.

**Tests.** Kruskal-Wallis across the three cases; pairwise Mann-Whitney with Holm
correction; ε² and Cliff's δ for effect size. Reliability: ICC(2,k) for the
agreement of the panel mean, Krippendorff's α (interval), mean pairwise Spearman,
and within-judge SD across the 3 repeats.

## 7. Exclusions — all explicit, none silent

**The generator's own lab is a separate stratum.** The artifacts were generated by
an OpenAI model, so `openai/gpt-5.6-sol` is not an independent rater of its own
lab's output. Primary results use the six independent judges; the OpenAI judge is
reported alongside in `self_preference.csv` and
`case_comparisons_generator_lab.csv`.

There is no self-preference to correct for. It scores its own lab's work
*harsher* than the panel on three of the four study × track combinations (bias
−0.42, −0.11, −0.09; the exception is study 1 inclusivity at +0.06), and it
correlates well with the panel (ρ 0.43–0.82). Run on its own it reaches the same
conclusions the panel does — inclusivity higher in case 3 (δ=−0.93 in both
studies), security flat — so including or excluding it does not change what the
data says.

**A non-discriminating judge is dropped from study 1 security.**
`mistralai/mistral-medium-3-5` returned 5 to every positively-worded statement and
1 to the two reverse-worded ones regardless of artifact: 86.6% fives, three
distinct values across 1,350 item scores, artifact-level SD **0.008** against
0.16–0.31 for every other judge. That is a fixed response pattern, not a
judgement, and retaining it halved security ICC (0.56 → 0.27) and drove
Krippendorff's α negative. It is a usable *inclusivity* judge in both studies.
`analyse.py` and `report.py` detect any such judge automatically by
artifact-level SD and name it; pass `--keep-degenerate` to retain.

Dropping it removes 90 judgements, so **2,457 judgements were produced and 2,367
enter the primary analysis** (35,505 item scores). Both counts are reported.

**Unscoreable artifacts.** An artifact that never served a page produced no
screenshots and so cannot be scored on the inclusivity track. Those records exist
with `ok: false` and `reason: "no_screenshots"` rather than being deleted — 21
records (study 1, `case_3/run_10`) and 42 (study 2, `case_3/run_02` and
`case_3/run_05`). They are still scored on security, since that track reads the
source.

**Known-broken artifacts (`--working-only`).** Two further study-2 artifacts,
`case_3/run_04` and `case_3/run_07`, serve HTTP 200 and screenshot successfully
but their client script dies on load, so a user sees a dead page. Excluding them
moves study 2's inclusivity result from H=3.465, p=0.177 to H=11.550, p=0.0031,
ε²=0.462. This exclusion is **not neutral** — all four affected artifacts are
from case 3, because that is the only case that produced any — so it must never
be reported on its own. Both variants are provided in `cross_study/`:
`report_all.txt` and `report_working_only.txt`. Study 1 predates the
client-script check, has no such signal, and is identical in both.

## 8. Headline results

So a reader knows what the tables should say. Full output in
`cross_study/report_all.txt`; every number below is reproducible from the CSVs.

**Case medians (artifact score, 1–5):**

| Study | Case 1 | Case 2 | Case 3 |
|-------|--------|--------|--------|
| 1 security | 3.644 | 3.778 | 3.689 |
| 1 inclusivity | 3.289 | 3.372 | **3.944** |
| 2 security | 4.489 | 4.506 | 4.511 |
| 2 inclusivity | 3.394 | 3.389 | **4.083** |

**Primary test — does the inclusivity specification change the scores?**

| Study | Track | H | p | ε² | Case 3 vs 1 (Cliff's δ) |
|-------|-------|---|---|-----|------------------------|
| 1 | security | 5.133 | 0.077 | 0.177 | −0.29 |
| 1 | inclusivity | 19.001 | **0.0001** | 0.679 | **−1.00** (complete separation) |
| 2 | security | 0.601 | 0.740 | 0.021 | −0.16 |
| 2 | inclusivity | 3.465 | 0.177 | 0.128 | −0.48 |
| 2 (working only) | inclusivity | 11.550 | **0.0031** | 0.462 | **−0.97** |

Asking for inclusivity raises inclusivity scores and does **not** measurably
lower security scores in either study. But in study 2 it does cost *working
software*: case 3 converged 4/10 against 10/10 and 10/10, served HTTP 200 8/10,
and had a live client script in only 6/10 (χ²=9.23, p=0.0099). That trade-off is
in artifact health, not in the security score.

**Cross-study.** Study 2's artifacts score 0.75–0.89 higher on security in every
case (p≤0.0004, δ 0.94–1.00) — same rubric, so this is comparable. Inclusivity is
statistically indistinguishable between studies, but see §5 before reading
anything into that.

**Best run per case**, offered as candidates for human evaluation:
study 1 `case_1/run_04` (3.633), `case_2/run_04` (3.711), `case_3/run_05`
(3.989); study 2 `case_1/run_01` (4.072), `case_2/run_05` (4.183),
`case_3/run_01` (4.583). Full ranking in `cross_study/05b_all_artifacts_ranked.csv`.

## 9. File formats

### `repeat_N.json` — one judgement

| Field | Meaning |
|-------|---------|
| `ok` | false when the judgement could not be produced; see `reason` |
| `artifact_id`, `case`, `run`, `track`, `judge`, `repeat` | identity |
| `judge_served` | the model the provider actually served |
| `rubric_file`, `rubric_sha256` | which rubric, and its exact content |
| `app_ts_sha256` | the artifact scored, checked against the manifest |
| `screenshot_count`, `screenshots_available`, `screenshots_sampled`, `screenshots` | what the judge saw |
| `scores` | `{"1": {"score": 1–5, "why": "..."}, …}` — raw, per item |
| `adjusted_scores` | after reverse coding |
| `constructs`, `overall` | derived, see §6 |
| `cost_usd`, `generation_id`, `judged_at`, `attempts` | provenance |

### `scores_long.csv` — the tidy primary table

One row per item score: `artifact_id, case, run, track, judge, repeat, item,
construct, raw_score, adjusted_score, reverse_coded, screenshot_count,
justification`. 18,585 rows for study 1 and 18,270 for study 2.

> **`artifact_id` is not unique across studies** — both use `case_N/run_NN`. Any
> join across the two must key on **study and artifact_id together**.

### `scores_artifact.csv` — one row per judgement

Adds `overall`, the five `c_<construct>` means, and provenance hashes.
Construct columns are **recomputed from the item scores** whenever the tables are
rebuilt, rather than trusting labels stored at judging time.

## 10. Limitations to carry into any write-up

1. **The inclusivity instrument is matched to the condition by design.** The
   original per-case rubric files are used unchanged, and case 3's rubric
   contains condition guidance that case 1's does not. Part of any inclusivity
   difference may be the rubric rather than the artifact. The judging is
   unblinded by construction.
2. **Security agreement is only moderate** — ICC 0.56 (study 1) and 0.72
   (study 2) after exclusions. Inclusivity is strong at 0.92 and 0.95.
3. **Study 1's rubric is internally inconsistent**: its narrative "Security
   Criteria" section lists SSRF and omits Cryptographic Failures, while its
   scored items cover Cryptographic Failures and not SSRF. Study 2's agree. The
   scored constructs are identical either way, so the comparison holds.
4. **Screenshot counts differ by case**, notably in study 2 (case 3 averages 5.4
   against ~11). Several inclusivity items concern progression across steps, so
   `screenshot_count` should be carried as a covariate.
5. **Verification instruments differ between studies.** Study 1 is frozen and
   predates the client-script check, the browser-exploration walkthrough and the
   TOTP-aware flow test. Boot statistics, flow pass rates and screenshot counts
   are **not comparable across studies**; judgement scores are.
6. **Flow-test results are LLM-mediated measurement**, not ground truth: the call
   sequence is model-derived, though pass/fail comes from real HTTP responses.
   Flow results never enter any score or statistic.

## 11. Reproducing

From the repository root:

```bash
uv run python run_batch.py   --software <study> --runs 10 --smoke-test --flow-test
uv run python run_capture.py --software <study> --runs 10
uv run python run_judge.py   --software <study> --repeats 3
uv run python analyse.py     --software <study> --drop-degenerate
uv run python report.py                       # cross-study tables
uv run python build_workbook.py               # all_results.xlsx
```

`run_judge.py --tables-only` rebuilds the CSVs from existing records with no API
calls. Judging is resumable: only readable successes and permanently unscoreable
cells count as done, so a crashed or rate-limited run is retried rather than
having its errors baked in.

**Cost.** Generation, as recorded in the manifests: $10.56 (study 1) and $22.36
(study 2 as it now stands; roughly $39 in total, including a discarded case-3
batch and a max-iterations pilot). Judging: $79.78 and $79.66. Every record
carries its own `cost_usd`, taken from the provider's usage accounting rather
than estimated from token counts.
