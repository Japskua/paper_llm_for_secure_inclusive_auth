## PARSED_TASKS
- Create a single runnable app.ts Bun HTTPS server that serves the complete application from inline HTML, CSS, and vanilla browser JavaScript, using certs/cert.pem and certs/key.pem with no external assets or network calls.
- Add HTTPS-only request handling and security headers including HSTS, a restrictive CSP, frame protection, MIME sniffing protection, referrer policy, and a generic production-safe error response without stack traces.
- Implement in-memory server-side session state with cryptographically random, per-session CSRF tokens stored in Secure, HttpOnly, SameSite cookies; require and validate the matching token on every state-changing endpoint.
- Implement a password-reset request endpoint that accepts a non-identifying account contact value, returns the same generic response for valid and invalid values, rate-limits repeated requests, and logs the simulated delivery only in the browser after receiving the mock result.
- Generate reset tokens using cryptographic randomness and store only a hashed token value with session/account binding, expiration, and unused status; never expose account identifiers or patient data in responses.
- Provide a reset-token verification route and UI that accepts either a reset-link token or manually entered token, rejects expired/used/invalid tokens with clear generic feedback, and rate-limits verification attempts.
- Implement reset confirmation that validates the reset token again, enforces a strong password policy, hashes the new password with Bun-supported bcrypt or Argon2 before storage, and invalidates the token after successful use.
- Implement a deterministic MFA challenge after successful password reset/login verification, with a usable mock code returned to the UI and logged through console.log in the browser; throttle failed MFA attempts and do not allow protected access until it succeeds.
- Implement login with password-hash verification, generic invalid-credential messages, per-session/account attempt throttling or temporary lockout, CSRF validation, and no disclosure of usernames or private account identifiers.
- Render a semantic, accessible single-page recovery flow for requesting a reset, entering a token, choosing a new password, completing MFA, signing in, and accepting the updated privacy conditions; ensure every internal navigation control works without dead links.
- Ensure all browser-rendered dynamic values are inserted as text rather than HTML, validate and sanitize all input formats server-side, avoid evaluating untrusted content, and use only application-owned inline scripts permitted by the CSP.
- Add protected privacy-acceptance handling that requires an authenticated server-side session and CSRF validation, prevents IDOR by operating only on the current session’s account, and logs the simulated acceptance in the browser console.
- Add clear source comments in app.ts mapping each security control and UI behavior to the applicable Requirement sections, including CSRF/access control, XSS prevention, HTTPS/token handling, authentication/MFA, and phishing/open-redirect safeguards.
- Display safe-authentication guidance in the UI stating that staff will not request passwords or codes by email/phone, do not implement external redirects, and allow only fixed internal application routes.
