## PARSED_TASKS
- Create a single runnable app.ts that starts a Bun HTTPS server using certs/cert.pem and certs/key.pem, serves the complete SPA from one route, and does not use local modules, build steps, frameworks, or external network calls.
- Implement HTTP-to-HTTPS enforcement and secure response headers including HSTS, a restrictive CSP, X-Content-Type-Options, X-Frame-Options, Referrer-Policy, and cache prevention for sensitive responses.
- Render a semantic, accessible password-recovery SPA with inline plain HTML, CSS, and vanilla browser JavaScript for account recovery request, reset-code/link verification, password change, sign-in, MFA verification, privacy-condition acceptance, and confirmation states.
- Implement server-managed sessions using cryptographically random, Secure, HttpOnly, SameSite cookies and a unique CSRF token per session; require and validate the matching token for every state-changing endpoint.
- Provide only narrowly scoped API routes for recovery, reset-token verification, password update, login, MFA verification, and privacy acceptance; reject unauthenticated, unauthorized, malformed, or cross-user requests without exposing account identifiers or patient data.
- Implement recovery requests with generic anti-enumeration feedback, cryptographically random reset tokens, single-use short expiration, server-side token storage, and both reset-link and manual-code submission paths.
- Return the deterministic mock recovery code/token only in the recovery API response for the browser to write with console.log, while avoiding it in server logs, rendered markup, URL fragments, and visible patient data.
- Store the mock account password only as a Bun-supported bcrypt or Argon2 hash, enforce a clear strong-password policy during reset, and invalidate existing authentication state after a successful password change.
- Implement login and reset/MFA verification rate limits or temporary lockouts keyed by session/client and account-safe identifiers, with clear non-sensitive feedback and no bypass through client-controlled fields.
- Implement a working simulated MFA step with a deterministic code that remains valid for testing, is logged only through browser console.log, and is required before authenticated privacy-condition acceptance.
- Ensure all user-controlled values are validated by allowlist/length rules and safely encoded before any UI rendering; use static client script only, avoid dynamic HTML/script injection, and prevent attacker-controlled navigation or redirect destinations.
- Include in-app safe-authentication guidance that warns users not to share passwords or verification codes through email or with callers, and make all internal navigation use implemented routes or controlled SPA state transitions.
- Add concise code comments in app.ts mapping the relevant server and client controls to Security Requirements 1 through 5, including CSRF/access control, XSS handling, HTTPS/configuration, authentication protections, and phishing/open-redirect defenses.
