## PARSED_TASKS
- Create a single runnable app.ts that starts a Bun HTTPS server using certs/cert.pem and certs/key.pem, serves the complete SPA at /, and handles missing certificates/errors without exposing stack traces.
- Add security response headers for every response: HSTS, restrictive CSP without untrusted script sources, X-Content-Type-Options, frame protection, referrer policy, and cache prevention for sensitive pages.
- Implement in-memory server-side session management with opaque Secure, HttpOnly, SameSite cookies and a unique CSRF token per session; do not expose account identifiers or patient data in browser output.
- Implement protected JSON endpoints for recovery initiation, reset-token verification, password update, and authentication; require and validate the session CSRF token for every state-changing request.
- Implement reset-token generation with cryptographically secure randomness, server-side expiry, single-use enforcement, session-bound recovery state, and generic recovery responses that do not reveal whether an account exists.
- Implement server-side rate limiting/temporary blocking for reset verification, password reset, and login attempts, with clear non-sensitive feedback and no account enumeration.
- Store the mock account password only as a Bun-supported bcrypt or Argon2 hash, verify it securely, and enforce a documented strong password policy when setting a replacement password.
- Implement a deterministic mock MFA verification step that remains valid without timeout; deliver its code and any reset token only through browser console.log, while permitting manual code/token entry in the UI.
- Build the inline vanilla HTML/CSS/JavaScript SPA recovery flow with semantic landmarks, visible numbered progress, one focused action per step, stable navigation, and explicit feedback for recovery request, verification, new password, MFA, sign-in, and privacy-condition confirmation.
- Persist non-sensitive in-progress recovery UI state in browser storage so a user can pause, refresh, and return without losing their current step; do not persist passwords, MFA codes, reset tokens, or authenticated session secrets.
- Add consistently visible help and safe-authentication guidance on each recovery screen, including that staff will never request a password or code by email; ensure no support action reveals private data.
- Ensure all client-rendered dynamic values are safely rendered as text rather than HTML, validate input formats on both client and server, and avoid evaluating user-controlled content, inline event attributes, untrusted scripts, redirects, and external network requests.
- Implement the post-authentication privacy-statement acceptance flow as a CSRF-protected, authenticated server action, with access control that prevents unauthenticated or cross-session access and a clear confirmation screen.
- Add clear code comments in app.ts mapping the relevant server and UI sections to the stated accessibility and OWASP/security requirements, and verify all internal navigation/actions work without additional files or build steps.
