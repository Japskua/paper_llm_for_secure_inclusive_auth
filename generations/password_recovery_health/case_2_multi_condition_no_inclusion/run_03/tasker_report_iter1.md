## PARSED_TASKS
- Create a single runnable app.ts that starts a Bun HTTPS server using certs/cert.pem and certs/key.pem, serves the complete HTML/CSS/vanilla-JS SPA, and exposes no local modules, build steps, or external assets.
- Enforce HTTPS-only operation and send production security headers on every response: HSTS, restrictive CSP with a per-response nonce for the required inline client script, X-Content-Type-Options: nosniff, X-Frame-Options: DENY, Referrer-Policy: no-referrer, and a restrictive permissions policy.
- Implement only explicit same-origin routes in app.ts, return generic error responses without stack traces or directory listings, and ensure unknown paths, parameters, and redirect destinations cannot disclose data or produce open redirects.
- Render a semantic password-recovery SPA with functional screens for recovery request, reset-token verification (including manual token entry), password replacement, MFA confirmation, sign-in confirmation, and updated-privacy acceptance.
- Implement a recovery-request endpoint that accepts a non-identifying account contact value, returns the same generic success response regardless of account existence, and browser-console-logs a deterministic mock delivery containing the returned recovery token for evaluation.
- Generate reset tokens with cryptographically secure randomness, store only a secure token digest with its session/account binding, expiry, use status, and attempt count in memory, and ensure each valid token can be used exactly once.
- Require token verification before password replacement, reject expired, invalid, already-used, cross-session, or over-attempt-limit tokens with clear but non-sensitive feedback, and throttle recovery and token-verification attempts per session.
- Implement CSRF protection by creating a cryptographically random token per session, sending it in the protected page state, and validating it on every state-changing endpoint (recovery initiation, token verification, password change, MFA verification, and privacy acceptance).
- Use secure session cookies (Secure, HttpOnly, SameSite=Strict, scoped path) and enforce server-side session ownership and authorization for every sensitive action so no client-supplied identifier can access another account or recovery flow.
- Enforce a strong password policy during replacement (minimum length and character diversity), reject passwords that fail it with actionable feedback, and store the replacement password only as a Bun-supported bcrypt or Argon2 hash, never plaintext.
- Implement deterministic mock MFA after password replacement with browser-console delivery logging, server-side attempt throttling, and a code that remains valid for evaluation until successfully used.
- Implement login/MFA attempt rate limiting or temporary lockout in in-memory state, return generic authentication failures, and avoid username/account enumeration in all authentication and recovery responses.
- Ensure all client-rendered dynamic values are inserted through safe text APIs rather than HTML interpretation, validate and length-limit every request field server-side, and prevent script injection, credential theft, and untrusted navigation from submitted data.
- Include visible anti-phishing and social-engineering guidance stating that hospital staff never request passwords or codes by email/phone and that users should verify the localhost HTTPS address before authenticating.
- Keep every simulated delivery and state transition internal: make no external network requests, log mock recovery/MFA delivery events only in the browser console, and document this behavior in the UI where relevant.
- Add clear source comments in app.ts mapping the HTTPS/headers, CSRF/access-control, input/output safety, token lifecycle, password hashing/MFA/rate limiting, and anti-phishing controls to Security Requirements 1 through 5.
