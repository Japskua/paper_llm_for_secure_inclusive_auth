## PARSED_TASKS
- Create a single runnable app.ts that starts a Bun HTTPS server using certs/cert.pem and certs/key.pem, serves the complete inline HTML/CSS/vanilla-JS SPA, and handles all application routes without external assets or network calls.
- Add production security configuration: redirect/reject non-HTTPS requests, set HSTS, CSP, X-Content-Type-Options, Referrer-Policy, and frame protection headers, and return generic error pages without stack traces or directory listings.
- Implement server-side session management with cryptographically random session IDs in Secure, HttpOnly, SameSite=Strict cookies and a unique CSRF token per session.
- Implement a CSRF-protected password-recovery request endpoint that accepts a sanitized account contact value, always returns a privacy-preserving generic response, rate-limits repeated requests, and does not disclose usernames or patient data.
- Generate cryptographically random password-reset tokens stored only server-side with an expiry and consumed flag; ensure each token is single-use, short-lived, unguessable, and cannot identify or access another user.
- Provide a recovery UI that allows both reset-link token handling and manual token entry, logs deterministic mock delivery details only in the browser console, and keeps the simulated code/token valid until successful use or its configured expiration.
- Implement token verification and password-update endpoints that require the session CSRF token, enforce token expiry/single-use rules, throttle invalid verification attempts, and return clear but non-sensitive feedback.
- Enforce a documented strong password policy in both client guidance and server validation, hash replacement passwords with Bun-supported bcrypt or Argon2 before in-memory storage, and never render, log, or retain plaintext passwords beyond request handling.
- Implement a simulated MFA verification step after reset-token validation, with a deterministic browser-console mock code, CSRF protection, attempt throttling, and a code that remains usable for the recovery flow.
- Implement a post-recovery sign-in and privacy-condition acceptance flow with hashed-password verification, login throttling/temporary lockout after repeated failures, session-based authorization, and no user-controlled object identifiers.
- Build semantic, accessible plain HTML recovery screens for account recovery, token entry, MFA, password creation, sign-in, privacy-statement acceptance, and confirmation; ensure every button, form, and internal navigation path works within app.ts.
- Prevent XSS by validating inputs, escaping all dynamic values before DOM insertion, avoiding untrusted HTML/script execution, and using only fixed inline client code permitted by the CSP.
- Add visible anti-phishing and social-engineering guidance stating that staff never request passwords or MFA codes by email/phone, and ensure all success navigation uses a fixed allowlist with no user-provided redirect URL.
- Add concise comments in app.ts mapping the server and client controls to each applicable Security Evaluation Requirement section and the single-file/Bun/mock-delivery requirements.
