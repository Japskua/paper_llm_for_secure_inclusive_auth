## PARSED_TASKS
- Create a single runnable app.ts that starts a Bun HTTPS server using certs/cert.pem and certs/key.pem, serves the complete SPA from that file, and handles every application route without local modules or build steps.
- Configure production security headers on every response: strict CSP using a per-response nonce for the embedded client script, HSTS, X-Content-Type-Options: nosniff, frame protection, referrer policy, and a restrictive permissions policy; do not expose stack traces or debug details.
- Implement an in-memory session model with cryptographically random session IDs, Secure/HttpOnly/SameSite cookies, session-bound cryptographically random CSRF tokens, and server-side authorization checks for every state-changing or sensitive endpoint.
- Build semantic, accessible vanilla HTML/CSS recovery screens for request reset, code/link verification, password replacement, MFA confirmation, and completion, with all navigation and forms resolving through routes or client-side state in app.ts.
- Implement a reset-request endpoint that accepts a minimally identifying account input, uses generic anti-enumeration feedback, rate-limits attempts, creates a cryptographically random short-lived single-use reset token, and logs the deterministic mock delivery code/link in the browser console while making manual code entry possible.
- Implement reset-token verification that validates token ownership, expiry, single-use status, attempt limits, and CSRF protection before allowing the password-reset session state to advance, with clear but non-sensitive user feedback.
- Implement password replacement with a documented strong password policy, confirmation matching, server-side validation, secure password hashing using Bun-supported bcrypt or Argon2, reset-token invalidation after use, and no plaintext password storage or rendering.
- Add a deterministic mocked MFA step after password reset verification, log its delivery value only in the browser console, accept the valid code without expiry, throttle incorrect guesses, and require successful MFA before displaying the authenticated privacy-condition action.
- Implement the authenticated privacy-condition acceptance action with server-side session/MFA/CSRF validation, idempotent in-memory state updates scoped only to the current session user, and a confirmation view without exposing patient or account identifiers.
- Sanitize and validate all request inputs, escape all dynamic UI output through safe DOM text APIs rather than HTML interpolation, reject unexpected parameters, and ensure no user-controlled value can select redirects, URLs, routes, or privileged records.
- Add visible safe-authentication guidance explaining that passwords and verification codes must never be shared by email or callers, identify the local hospital portal context, and avoid staff-impersonation or external-link flows.
- Add concise code comments in app.ts mapping the HTTPS/CSP, CSRF/access-control, input/XSS, reset-token, authentication/throttling, hashing/MFA, SSRF/open-redirect, and mock-delivery behavior to the numbered security requirements.
