## PARSED_TASKS
- Create a single runnable app.ts that starts a Bun HTTPS server using certs/cert.pem and certs/key.pem, serves the application at /, redirects HTTP requests to HTTPS, and does not expose debug errors or directory listings.
- Add security headers to every response: HSTS, a restrictive CSP that permits only the app’s own inline hashed/nonced client script and styles, X-Content-Type-Options: nosniff, X-Frame-Options: DENY, Referrer-Policy: no-referrer, and a restrictive Permissions-Policy.
- Embed the complete semantic HTML, minimal CSS, and vanilla browser JavaScript in the app.ts HTML response, with no external assets, frameworks, local modules, remote fetches, or build step.
- Implement an initial password-recovery screen that accepts an account recovery identifier without revealing whether a matching account exists, and render all dynamic user-controlled text with DOM text APIs rather than HTML interpolation.
- Create an in-memory session store with cryptographically random session IDs and unique CSRF tokens, issue the session cookie with Secure, HttpOnly, SameSite=Strict, and Path=/ attributes, and require the CSRF token on every state-changing endpoint.
- Implement a same-origin recovery-request endpoint that validates request shape and CSRF token, rate-limits requests by session, and returns a generic success response regardless of account existence.
- Generate reset tokens with cryptographically secure randomness, bind each token only to its originating recovery session, store only a token hash with issuance and expiration metadata, and make each token single-use.
- On a successful recovery request, return the deterministic test reset code only in the response needed by the app and log the simulated delivery plus code using console.log in the browser; do not log or display account identifiers.
- Provide a verification screen that supports both following the internally generated reset-link route and manually submitting the delivered reset code, while validating route/query values against an allowlist and never redirecting to a user-provided URL.
- Implement a reset-token verification endpoint that validates session binding, token hash, expiry, single-use status, CSRF protection, and rate limits; return clear but non-sensitive invalid/expired feedback.
- Implement a new-password screen available only after successful reset-token verification, enforce a documented strong password policy, require matching confirmation, and avoid retaining or rendering submitted passwords.
- Store replacement passwords only as hashes using Bun-supported bcrypt or Argon2 functionality, invalidate the consumed reset token and any prior authenticated sessions after a successful password change, and log the simulated update only in the browser console.
- Add a sign-in screen that uses the in-memory hashed password record, generic authentication errors, session regeneration on success, CSRF validation, and per-session throttling or temporary lockout after repeated failed attempts.
- Add a simulated MFA step after valid password sign-in using a deterministic code that is logged in the browser console, rate-limit MFA guesses, and require successful MFA before creating the authenticated account session.
- Protect the privacy-statement and appointment-confirmation routes with server-side authenticated-session and MFA checks, so no query parameter, token, or guessed identifier can access another user’s data or actions.
- Implement the privacy acceptance action with CSRF validation and authenticated-session authorization, store acceptance only for the current session’s mock account, and show an appointment-booking confirmation without exposing patient records or identifiers.
- Add visible safe-authentication guidance throughout recovery and login screens, including that staff never request passwords or codes by email/phone and that users should verify the localhost HTTPS address.
- Add concise code comments in app.ts mapping the server and client protections to each applicable Security Evaluation Requirement section, including CSRF/access control, XSS/output handling, HTTPS/header configuration, token security, authentication throttling, hashing/MFA, and redirect/SSRF protections.
- Verify every displayed internal navigation control and form targets an implemented route or handler, all mock events use browser console.log, and bun app.ts runs the complete flow with no network calls.
