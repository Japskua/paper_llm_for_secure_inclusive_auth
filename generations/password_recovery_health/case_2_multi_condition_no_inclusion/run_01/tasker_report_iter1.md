## PARSED_TASKS
- Create a single runnable app.ts that starts a Bun HTTPS server using certs/cert.pem and certs/key.pem, serves the complete SPA from one route, and does not import local project files or use build tooling.
- Configure HTTPS-only security behavior: redirect or reject non-HTTPS requests and send HSTS, restrictive CSP with a per-response nonce, frame protection, MIME sniffing protection, referrer policy, and cache-control headers.
- Implement a semantic password-recovery SPA in the server-rendered HTML template using embedded CSS and nonce-authorized vanilla JavaScript only; provide accessible labels, status messages, and a clear recovery progress flow.
- Implement the recovery request screen with a generic confirmation response that does not reveal whether an account exists, and display safe-authentication guidance that passwords and codes must never be shared with staff or email senders.
- Generate a cryptographically random reset token and per-session CSRF token on a successful recovery request; store only server-side token metadata including expiry, used state, session binding, and attempt counters.
- Simulate reset delivery entirely in browser console.log, returning the deterministic testing code/token to the browser only for the mock flow; support both following the reset link and manually submitting the displayed code.
- Validate reset tokens server-side for existence, session binding, cryptographic comparison, expiration, and single use; return clear but non-sensitive invalid, expired, or already-used feedback.
- Require and validate the session-specific CSRF token on every state-changing recovery, token-verification, password-reset, MFA-verification, and sign-in request; reject missing or invalid tokens without performing the action.
- Add server-side rate limits and temporary lockouts for recovery-code verification, MFA verification, and sign-in failures, with generic user-facing throttling feedback.
- Implement a strong-password form that enforces a documented minimum length and character diversity policy, confirms matching passwords, and never renders submitted values back into HTML or logs them.
- Hash the new password with Bun-supported bcrypt or Argon2 before storing it in in-memory state; ensure no plaintext password is persisted, returned, or written to browser/server logs.
- Require a mock MFA step after password reset using a generated verification code that remains valid for the academic test until successfully used; log its mock delivery in the browser console and throttle invalid attempts.
- Create an authenticated confirmation screen that allows Helena to accept the updated privacy conditions only after successful reset, MFA, and sign-in; enforce authorization server-side and avoid accepting user-selected account identifiers.
- Ensure all request parsing, validation, and response rendering treat input as untrusted: use strict allowlists and length limits, escape dynamic HTML output, avoid unsafe DOM sinks, and prevent client-controlled redirects.
- Provide only fixed internal navigation targets for recovery, verification, reset, MFA, sign-in, and confirmation states; validate any return path against this allowlist and reject external or malformed destinations.
- Add concise code comments in app.ts mapping the HTTPS/TLS, CSRF/access-control, XSS/output handling, token security, password hashing/MFA/throttling, and anti-phishing protections to the numbered security requirements.
- Handle unknown routes and malformed requests with generic responses that expose no stack traces, directory contents, account data, usernames, or private identifiers.
