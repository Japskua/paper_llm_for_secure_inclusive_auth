## SUMMARY

The artifact is a single `app.ts` Bun HTTPS SPA with substantial server-side security controls, responsive mobile UI, simulated MFA codes logged in the browser, and a complete intended enrolment flow. However, it has a critical TOTP/Base32 decoding defect that prevents a real authenticator app provisioned from the displayed QR code/setup key from generating codes the server can verify. It also has a broken backup-code regeneration confirmation due to a JavaScript name collision, and the login credentials required for the deterministic mock are not presented to the user. Therefore, the artifact cannot be accepted as fully functional.

## FUNCTIONAL_CHECK

- **PASS — Single-file Bun application with no framework, external assets, build tooling, or compilation requirement.**  
  The HTML, CSS, browser JavaScript, and Bun server are contained in `app.ts`. It uses Bun APIs directly and does not import external frontend assets or libraries.

- **PASS — Bun HTTPS server uses the required local TLS certificate paths.**  
  The server is configured with `file("certs/cert.pem")` and `file("certs/key.pem")`, and rejects non-HTTPS requests.

- **PASS — Mobile-responsive, legible, dyslexia-conscious UI is substantially implemented.**  
  The UI uses a constrained mobile layout, large controls, generous spacing, plain-language short instructions, code examples, icons, non-moving content, visible step indicators, and accessible input attributes such as `autocomplete="one-time-code"`.

- **PASS — Browser-side simulated values are logged and MFA values can be used in the intended UI.**  
  Identity codes, authenticator setup values/current codes, and recovery codes are returned by the API and logged through browser `console.log`. Setup keys and recovery codes are also available in the rendered UI with copy controls.

- **FAIL — Authenticator provisioning through the displayed QR code/manual setup key does not interoperate with a real TOTP authenticator.**  
  In `base32Bytes`, every Base32 character increments `bits` by `8` rather than `5`:
  ```ts
  value = (value << 5) | n; bits += 8;
  ```
  This incorrectly decodes the displayed Base32 setup secret before calculating server-side TOTPs. An authenticator app scans/uses the correct Base32 secret, while the server computes OTPs from different bytes. Consequently, codes generated by a real authenticator app will fail server verification.

- **FAIL — The backup-code regeneration confirmation is broken.**  
  The view-rendering function named `confirm()` shadows the browser’s `window.confirm()` function. In `backup()`:
  ```js
  if(!confirm("Regenerate backup codes? Your current codes will stop working."))return;
  ```
  this calls the local `confirm` page-rendering function instead of the native confirmation dialog. It returns `undefined`, making the negation true, and regeneration proceeds immediately. The user is not actually asked to confirm invalidating existing recovery codes.

- **FAIL — The deterministic mock sign-in is not usable from the UI without inspecting source code.**  
  Login requires the hard-coded password `bank-demo`, but the UI only gives an email example and never explains the simulation credential. A user following the interface cannot know how to complete the first step. The mock credentials should be explicitly provided in the browser UI or browser console as a simulation aid.

- **PASS — Manual authenticator setup is offered alongside QR provisioning.**  
  The application displays the setup secret, supports copying it, offers hide/show behavior, and explains that users can choose “enter setup key” in an authenticator app.

- **PASS — Recovery codes are generated securely, displayed only for the authenticated owner, copyable, hashed at rest, expiring, and single-use.**  
  Recovery codes use cryptographic randomness, are protected by a server-side peppered SHA-256 hash, have a one-year expiry, are deleted after successful use, and are rate-limited.

- **PASS — Server-side authorization and IDOR protections are substantially implemented.**  
  MFA account data is resolved from `session.userId`; client-supplied account/user identifiers are not accepted. MFA-changing endpoints require an authenticated owner and, where appropriate, a completed identity check.

- **PASS — CSRF protection is applied to state-changing actions.**  
  POST requests require a per-session `X-CSRF-Token`, and the server additionally checks the request origin against trusted local HTTPS origins.

- **PASS — Session security controls are substantially implemented.**  
  Sessions use cryptographically generated IDs, `HttpOnly`, `Secure`, and `SameSite=Strict` cookies. Sessions are rotated after login, have idle and absolute expiry checks, and are invalidated on logout.

- **PASS — Security headers and CORS posture are substantially implemented.**  
  Responses include CSP with a per-page nonce, HSTS, `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `frame-ancestors 'none'`, restrictive permissions/referrer policies, and no permissive CORS headers.

- **PASS — Server-side validation, output handling, expiry, single-use handling, and lockout logic are substantially implemented.**  
  Email/code/recovery-code formats are validated, API errors are generic where suitable, values are written with `textContent` in the browser, and identity/recovery verification has expiration and lockout handling. TOTP counters are tracked to prevent reuse of an accepted TOTP counter.

## FAILING_ITEMS

- `base32Bytes()` is incorrect because it uses `bits += 8` for each Base32 symbol instead of `bits += 5`. This makes server-generated TOTP values incompatible with the displayed provisioning secret and QR URI.
- Recovery-code regeneration does not require user confirmation because the local `confirm()` renderer shadows the native `window.confirm()` method.
- The mock login password (`bank-demo`) is not disclosed in the application UI or browser console, leaving the sign-in step unusable for a normal evaluator/user.

## NEW_TASKS

1. Correct Base32 decoding in `base32Bytes()` by changing `bits += 8` to `bits += 5`; then verify that an RFC-compliant authenticator using the displayed setup key generates a code accepted by `/api/authenticator/confirm`.
2. Rename the `confirm()` view-rendering function (for example, to `authenticatorConfirm()`) and update `render()` accordingly, so recovery regeneration can call `window.confirm(...)` correctly.
3. Add clear simulation sign-in guidance at the sign-in screen, such as “For this practice setup, use `marcus@example.com` and password `bank-demo`,” while keeping the real credential-validation error generic.

## DECISION

FAIL
