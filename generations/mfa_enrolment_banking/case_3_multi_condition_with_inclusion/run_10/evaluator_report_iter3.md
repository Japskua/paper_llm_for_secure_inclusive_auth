## SUMMARY

The artifact is a well-structured single-file Bun HTTPS application with strong coverage of session ownership, CSRF checks, TLS, encrypted OTP-secret handling, recovery-code hashing, input validation, and a mobile-oriented accessibility design. However, it has a blocking functional defect: the authenticator provisioning URI is too large for the hard-coded Version 6 QR encoder, so the MFA enrolment flow cannot progress past authenticator setup. It also has security issues in lockout handling and CSP nonce reuse. Therefore, the artifact cannot be accepted as-is.

## FUNCTIONAL_CHECK

- **Single `app.ts` artifact containing Bun server, HTML, CSS, and vanilla browser JavaScript — PASS**
  - The application is wholly contained in one file.
  - It uses `Bun.serve()` and embeds the HTML/CSS/client JavaScript directly in the TypeScript file.
  - No framework, bundler, compiler pipeline, external asset, or network dependency is used.

- **Bun HTTPS server using the provided certificate paths — PASS**
  - The server reads `certs/cert.pem` and `certs/key.pem`.
  - `Bun.serve()` is configured with `tls: { cert, key }`.

- **Responsive, mobile-legible SPA UI — PASS**
  - The viewport meta tag is present.
  - The layout constrains content to a phone-friendly width and uses legible font sizing, generous spacing, large form controls, and full-width primary buttons.
  - The UI uses plain wording and consistently identifies the current step.

- **Dyslexia-inclusive UX requirements — PARTIAL / FAIL**
  - Positive: the design avoids dense paragraphs, uses generous spacing, includes examples, avoids auto-updating content, includes help on every screen, and provides copy/select fallbacks.
  - Failure: the core authenticator setup screen cannot render successfully because the QR encoder throws an error for the generated provisioning URI.
  - Failure: recovery codes cannot be revealed again after leaving the backup-code screen; the only available path is regeneration, which invalidates the prior set. This does not fully meet the requirement to let users reveal/hide/re-request codes without penalty.

- **Identity verification simulation works and supports re-requesting a code — PASS**
  - Identity codes are securely generated, returned in the mock API response, displayed for test use, and logged through browser `console.log`.
  - Codes are time-bound and marked as used after successful verification.
  - The UI provides a “Send a new code” action.

- **Authenticator provisioning and verification work end-to-end — FAIL**
  - The provisioning URI generated by `/api/mfa/provision` exceeds the QR encoder’s stated maximum of 134 bytes.
  - The URI is approximately 142 bytes because it includes `algorithm=SHA1`, `digits=6`, and `period=30`.
  - The client-side `qr(uri)` function throws `Error("Setup code is too long for this QR symbol.")`.
  - As a result, the setup card and verification form are not rendered, blocking the user from enrolling MFA.

- **QR code and manual setup-key options are offered — FAIL**
  - The intended UI includes both a QR code and a manually copyable setup key.
  - In practice, neither is usable because QR generation throws before the containing setup UI is appended.
  - This violates the requirement that provisioning options function correctly.

- **Backup recovery-code generation, display, copying, printing, and one-time use — PASS**
  - Recovery codes are generated with cryptographic randomness.
  - They are shown in the UI, can be copied, and can be printed/saved as PDF.
  - The browser console receives the mock values as required for testing.
  - Server-side recovery-code values are PBKDF2-derived with unique random salts and are removed after successful use.

- **All internal navigation/actions function correctly — FAIL**
  - Navigation actions are implemented as SPA state transitions and mostly work.
  - However, the main progression from authenticator provisioning to verification is blocked by the QR exception, so the enrolment flow does not function completely.

- **Server-side authorization and IDOR prevention on MFA endpoints — PASS**
  - MFA endpoints use `owner()` to require a current authenticated session, the expected server-side session stage, and a server-derived `userId`.
  - No client-controlled user/account identifier is accepted by MFA endpoints.
  - Manipulated or guessed account identifiers cannot select another account.

- **CSRF protection on state-changing requests — PASS**
  - State-changing endpoints require the `X-CSRF-Token` header.
  - The token is held in server-side session state and is rotated after identity verification.
  - Session cookies use `SameSite=Strict`.

- **Secure cookie configuration — PASS**
  - The session cookie includes `HttpOnly`, `Secure`, `SameSite=Strict`, and `Path=/`.
  - The `__Host-` cookie naming convention is used without a `Domain` attribute.
  - Logout invalidates the server session and expires the cookie.

- **Required security headers and restricted CORS — FAIL**
  - Positive: CSP, HSTS, `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `frame-ancestors 'none'`, no-store caching, and restricted CORS handling are implemented.
  - Failure: the CSP nonce is generated once at server startup and reused for every response. A CSP nonce must be generated per HTML response; a static nonce defeats the purpose of nonce-based CSP if markup injection becomes possible.

- **No sensitive secrets in server logs, URLs, browser storage, or error output — PASS**
  - No server-side logging of OTPs, secrets, recovery codes, or tokens is present.
  - Secrets are not placed in URLs or browser storage.
  - The browser console deliberately logs mock test values, which is explicitly required by the deliverables.
  - Generic server error messages are used.

- **Cryptographic protection of OTP secrets and recovery codes — PASS**
  - OTP secrets are encrypted using AES-GCM with a generated AES-256 key.
  - Recovery codes are generated with secure randomness and stored as PBKDF2-SHA-256 derived values using unique salts and 210,000 iterations.
  - TOTP verification uses HMAC-SHA-1 as specified by RFC 6238 and accepts a bounded clock-skew window.

- **HTTPS enforcement and HSTS — PASS**
  - The service is configured as TLS-only and includes HSTS.
  - There is no plain HTTP listener in the artifact.

- **Input validation, output handling, and redirect safety — PASS**
  - Email, phone, OTP, manually entered secret, and recovery-code inputs are validated server-side.
  - Client-rendered dynamic text generally uses `textContent`.
  - No redirect endpoint or externally controlled redirect target exists.
  - No SQL/database layer exists, so SQL injection is not applicable to this mock implementation.

- **Verification-code entropy, expiry, single use, and lockout — FAIL**
  - Positive: identity codes have secure entropy, expire after ten minutes, and are marked single-use. Recovery codes are consumed after use.
  - Failure: identity-verification lockout can be bypassed by calling `/api/identity/request` again. That endpoint resets `identityFailures` to `0` and clears `identityLockedUntil`, allowing unlimited cycles of five guesses followed by a re-request.
  - The endpoint must preserve an active lockout and must not clear failed-attempt counters/lockout state until the lockout period has elapsed.

- **Secure session lifecycle — PASS**
  - The pre-authentication session is replaced after successful sign-in, mitigating session fixation.
  - Idle and absolute expiration are checked.
  - Sessions are invalidated and removed on logout.

- **Mock values are deterministic as required — FAIL**
  - The requirements explicitly request deterministic mock values for simulated delivery/provisioning testing.
  - The implementation generates random identity codes and recovery codes, and derives TOTP values from the current time.
  - They are exposed to the browser console for testing, but they are not deterministic across runs.

## FAILING_ITEMS

- The hard-coded QR Version 6-L encoder only accepts up to 134 payload bytes, while the generated `otpauth://` URI is longer. The QR generator throws, preventing the authenticator setup UI and verification form from rendering.
- The MFA enrolment journey is therefore incomplete and cannot be completed through the normal UI.
- The identity-code lockout is bypassable because `/api/identity/request` resets both failed-attempt count and lockout state, including when a lockout is active.
- The CSP nonce is global (`const nonce = token(18)`) and reused for every HTML response rather than generated per response.
- Recovery codes cannot be safely re-shown after the user navigates away from the initial backup-code screen; regeneration replaces existing codes rather than offering a reveal/hide mechanism.
- The implementation does not use deterministic mock values despite that explicit requirement.

## NEW_TASKS

1. Replace the fixed Version 6 QR generator with a QR implementation that supports the full generated provisioning URI length, or shorten the URI to fit the implemented QR capacity while preserving valid TOTP defaults and interoperability.
2. Add an automated/manual flow check ensuring `/api/mfa/provision` renders a scannable QR code, copyable setup key, and usable OTP verification form without throwing client-side errors.
3. Change `/api/identity/request` so it checks and enforces `identityLockedUntil` before issuing a new code, and does not reset lockout/failure state while a lockout is active.
4. Generate a fresh CSP nonce for each HTML response and use that same per-response nonce in both the `Content-Security-Policy` header and the inline `<style>`/`<script>` elements.
5. Add a secure recovery-code visibility flow that lets the user hide/show the currently displayed codes before completion, and clearly explain that codes cannot be recovered after leaving the screen unless a replacement set is intentionally generated.
6. Align mock-code behavior with the deterministic-testing requirement, using clearly scoped deterministic test values while retaining explicit browser-console-only mock logging and preserving the intended verification behavior.

## DECISION

FAIL
