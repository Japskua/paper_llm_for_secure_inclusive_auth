## SUMMARY

The artifact is a single-file Bun HTTPS SPA with a mostly solid server-side security model: authenticated session ownership, CSRF checks, secure cookies, TLS, restrictive headers, cryptographic secret handling, rate limits, and functional mock verification flows are largely implemented correctly. However, it does not fully meet the MFA UX requirements because the displayed “QR code” is not a scannable QR code, and restored states can present unusable empty secret/code-copy controls. Required reveal/hide controls for sensitive setup and recovery values are also absent.

## FUNCTIONAL_CHECK

- **Single `app.ts` Bun server with inline HTML, CSS, and vanilla browser JavaScript — PASS**
  - The server, page template, CSS, and client logic all exist in one `app.ts`.
  - It uses `Bun.serve` directly and does not require a bundler, framework, compilation pipeline, or external assets.

- **HTTPS/TLS using the provided certificate paths — PASS**
  - Bun is configured with `certs/cert.pem` and `certs/key.pem`.
  - Secure cookies and HSTS are configured consistently with HTTPS use.

- **Mobile-responsive, readable MFA SPA — PASS**
  - The page uses a constrained mobile-width layout, responsive breakpoint, legible font sizing, spacing, large controls, short instructions, examples, and a predictable six-step progress display.
  - There are no animations, flashing elements, or reading timers.

- **Sign-in, identity verification, authenticator setup, OTP verification, recovery-code creation, completion, and logout flows — PASS**
  - The main enrolment sequence works server-side.
  - The client displays browser-console mock identity codes, authenticator OTPs, and recovery codes as required for testing.
  - Identity codes are verified, OTPs are checked using TOTP, recovery codes can be verified once, and logout invalidates the session.

- **Actual QR-code provisioning option — FAIL**
  - The element labelled as an “Authenticator QR code” is generated by `qrVisual()`, which creates a seeded decorative grid.
  - It does not encode the `otpauth://` provisioning URI in a standards-compliant QR format and cannot be scanned by an authenticator application.
  - This fails the requirement to offer a usable QR-code provisioning option.

- **Manual authenticator provisioning and clipboard support — PASS**
  - The Base32 secret and provisioning URI are shown and have copy controls.
  - The six-digit authenticator code can be entered manually.
  - Browser clipboard failure is handled with a clear fallback instruction.

- **State restoration and retry/re-request UX — FAIL**
  - If the browser refreshes while the session is at the `otp` stage, `/api/state` deliberately does not return the secret or provisioning URI, but the client still renders an empty QR visual and empty copyable fields.
  - The “Copy” controls then copy empty strings and the user is not clearly told that fresh setup details must be requested.
  - If refreshed at the recovery stage, the UI correctly says codes are not shown after refresh, but still renders “Copy all codes,” which copies an empty string.
  - This creates misleading and non-functional controls in valid session states.

- **Reveal, hide, and re-request sensitive code support — FAIL**
  - Identity-code resend, fresh authenticator setup, and recovery-code regeneration are implemented.
  - However, the client does not provide reveal/hide controls for the manually displayed Base32 secret, provisioning URI, or currently displayed recovery codes.
  - Sensitive values remain permanently visible while on their screen, contrary to the requirement to let users reveal and hide codes without penalty.

- **Server-side authorization and IDOR prevention — PASS**
  - MFA endpoints use the server-side session from the HttpOnly cookie.
  - Client-provided `userId`, `accountId`, and redirect fields are explicitly rejected.
  - There is no user identifier route parameter or request field that can be manipulated to access another user’s MFA state.

- **CSRF protection for state-changing endpoints — PASS**
  - State-changing endpoints require a per-session CSRF token through `X-CSRF-Token`.
  - Requests are additionally checked against trusted origins.
  - Session cookies are `SameSite=Strict`.

- **Secure headers and clickjacking protections — PASS**
  - Responses include CSP, HSTS, `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `frame-ancestors 'none'`, `Referrer-Policy`, `Cache-Control: no-store`, and a restrictive Permissions Policy.
  - CSP uses a per-page nonce for inline page CSS and JavaScript.

- **Session security — PASS**
  - Session IDs are cryptographically random.
  - The session is rotated after authentication.
  - Idle and absolute session expiry are enforced.
  - Logout deletes the session and clears the cookie.
  - Cookies use `HttpOnly`, `Secure`, and `SameSite=Strict`.

- **Cryptographic handling of OTP secrets and recovery codes — PASS**
  - OTP secrets are generated using cryptographic randomness and encrypted in memory with AES-GCM.
  - Recovery codes are generated with cryptographic randomness and stored as salted PBKDF2 hashes.
  - Identity codes are stored as keyed HMAC representations rather than plaintext.
  - Client-side persistent storage is not used.

- **Verification-code lifetime, single-use behavior, and throttling — PASS**
  - Identity codes are time-bound and single-use.
  - Authenticator enrolment verification is only accepted once before advancing.
  - Recovery codes are single-use and expiry-bound.
  - Failed attempts trigger a five-minute lockout after five failures.

- **Input validation, XSS prevention, and redirects — PASS**
  - Inputs are type-checked, length-limited, and format-validated server-side.
  - No database queries exist, so SQL injection is not applicable.
  - The page does not inject user-controlled values into `innerHTML`.
  - Redirect input is rejected and no external redirects are implemented.

- **No external network calls or external assets — PASS**
  - The application uses same-origin fetch calls only.
  - There are no CDN imports, external images, external scripts, analytics calls, or external API calls.

## FAILING_ITEMS

- The “QR code” is a decorative pseudo-random grid, not an actual QR code encoding the authenticator provisioning URI. Authenticator apps cannot scan it.
- Refreshing during the authenticator OTP stage renders blank manual setup fields, a meaningless pseudo-QR image, and Copy buttons that copy empty values.
- Refreshing during the recovery-code stage leaves “Copy all codes” active even though no recovery codes are available in client memory; it copies an empty string.
- The UI lacks reveal/hide controls for exposed sensitive values, including the Base32 secret, provisioning URI, and recovery codes.

## NEW_TASKS

1. Replace `qrVisual()` with a real, standards-compliant QR-code encoder rendered locally in the page (for example, SVG or canvas) that encodes the exact `otpauth://` provisioning URI, without adding external network dependencies.

2. Update OTP-stage rendering so that when `secret` or `uri` is unavailable after a page refresh, the page does not render blank secret fields, copy buttons, or a QR image; instead, show a clear explanation and one prominent “Get fresh setup details” action.

3. Update recovery-stage rendering so that when recovery codes are unavailable after refresh, all copy controls are hidden or disabled and the primary available action is to generate replacement recovery codes.

4. Add accessible show/hide controls for the displayed Base32 secret, provisioning URI, and recovery-code list while retaining the existing copy and re-request/regenerate options.

## DECISION

**FAIL**
