## SUMMARY

The artifact is a single-file Bun + HTML/CSS/vanilla-JS MFA enrolment application with strong coverage of session handling, CSRF, TLS, headers, server-side step enforcement, encrypted OTP-secret storage, hashed recovery codes, and mobile-oriented UX. However, it does not correctly interoperate with the authenticator URI it presents as a TOTP QR setup option: the server’s OTP algorithm and time period do not match the standard/default values implied by the `otpauth://` URI. There is also a defect in the custom QR format-information placement and a small inclusivity/help coverage gap. Therefore, it cannot be accepted as fully functional.

## FUNCTIONAL_CHECK

- **PASS — Single-file Bun application with no framework, bundler, compiler, or external assets**
  - The server, HTML, CSS, and browser JavaScript are all contained in `app.ts`.
  - It uses `Bun.serve` directly and does not depend on external assets or network calls.

- **PASS — TLS/HTTPS enforcement**
  - Startup refuses to run without `certs/cert.pem` and `certs/key.pem`.
  - `Bun.serve` is configured with TLS material.
  - Non-HTTPS requests are rejected with HTTP 426.
  - HSTS is sent in response headers.

- **PASS — Responsive, mobile-oriented, dyslexia-conscious UI**
  - The page uses a viewport meta tag, a constrained mobile-friendly layout, readable font sizing, generous spacing, visible focus states, short instructions, icons, and no moving/auto-updating UI.
  - Inputs include examples and suitable `autocomplete`/`inputmode` attributes.
  - Recovery codes support copy and download, and the authenticator secret supports copy.

- **PASS — Clear MFA step flow and server-side step enforcement**
  - The flow is sign-in → identity check → authenticator setup → backup codes → completion.
  - The server enforces stages for identity verification, authenticator setup, backup generation, and completion.
  - Manipulating the client-side visible view does not bypass the server-side stage checks.

- **PASS — Identity-code mock delivery and verification**
  - Identity codes are generated with `randomBytes`, hashed server-side, time-bound, single-use, and returned to the browser only for testing.
  - The browser logs the testing code via `console.log`.
  - Resending a code invalidates the previous code.
  - Validation errors identify the problem and provide a corrective action.

- **FAIL — Authenticator QR/provisioning flow is not consistent with the server’s OTP verification**
  - The provisioning URI is:
    - `otpauth://totp/...`
    - does not specify `algorithm=SHA256`
    - does not specify `period=600`
  - Standard authenticator applications therefore interpret it as standard TOTP, normally HMAC-SHA1 with a 30-second period.
  - The server instead calculates `HMAC-SHA256(secret, floor(Date.now() / 600000))`, a 10-minute custom interval.
  - A code generated by an authenticator app after scanning the QR code will generally not verify. Only the server-returned testing code/manual mock path works.
  - This violates the expectation that the offered provisioning URI/QR option works.

- **FAIL — Custom QR implementation has an incorrect format-information placement**
  - In `renderQr`, the horizontal format-information placement writes the `i === 8` format bit to `(8, 6)`:
    ```js
    else set(8,14-i,v);
    ```
  - For `i === 8`, this should be placed at `(8, 7)`; column 6 is a timing-pattern module and must be skipped.
  - The code consequently overwrites a timing module and leaves a required format-information module incorrect. Although some QR readers may recover from the redundant vertical format copy, this is not a reliable or standards-correct QR encoder.

- **PASS — Manual authenticator setup option is available**
  - The raw setup secret is visibly provided, can be copied, can be hidden/revealed, and the user can manually enter an authenticator code.
  - The code-entry field supports OTP autofill.

- **PASS — Backup-code generation, storage, display, regeneration, and one-time use**
  - Backup codes are generated using cryptographically secure randomness.
  - The server stores only hashes of recovery codes.
  - Codes can be copied, downloaded, hidden/revealed, regenerated, and tested.
  - Used codes are marked unavailable and cannot be used again.

- **PASS — Server-side authorization and IDOR resistance**
  - Authenticated endpoints obtain the account exclusively from the opaque server-side session.
  - No user/account identifiers are accepted from client requests for MFA operations.
  - Requests cannot select or modify another account’s MFA settings through guessed identifiers.

- **PASS — CSRF protection for state-changing operations**
  - Mutating endpoints require a matching `X-CSRF-Token`.
  - State-changing requests also check same-origin `Origin` values where supplied.
  - Session cookies are `HttpOnly`, `Secure`, and `SameSite=Strict`.

- **PASS — Secure session lifecycle**
  - Session identifiers are high-entropy opaque values.
  - Sign-in deletes the pre-authentication session and creates a fresh authenticated session, preventing session fixation.
  - Idle and absolute timeouts are enforced.
  - Logout deletes the server session and expires the cookie.

- **PASS — Rate limiting, lockouts, code expiry, and single-use semantics**
  - Identity, authenticator, recovery-code, and sign-in attempts have failure counters and lockouts.
  - Identity-code requests are rate-limited.
  - Identity codes expire and are single-use.
  - Recovery codes are single-use.
  - The pending authenticator confirmation code is limited to the setup lifetime and cannot be reused after stage advancement.

- **PASS — Secure configuration and response headers**
  - CSP uses nonces for inline script and style.
  - HSTS, `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, CSP `frame-ancestors 'none'`, `Referrer-Policy`, and `Cache-Control: no-store` are present.
  - CORS only emits `Access-Control-Allow-Origin` for the exact same origin.
  - Generic errors are returned rather than stack traces.

- **PASS — Sensitive data is not persisted in browser storage or URLs**
  - The application does not use `localStorage` or `sessionStorage`.
  - Secrets and codes are not placed in URL query parameters.
  - The session identifier is held in an HttpOnly cookie.

- **FAIL — Help is not available on every enrolment step**
  - Sign-in, identity, authenticator, and backup screens contain a “Need help?” link.
  - The success/recovery-code testing screen has no help link or equivalent easy-to-find help affordance.
  - This does not fully meet the requirement that brief help or hints be easy to find at every step.

- **FAIL — Help copy makes an inaccurate expiry promise**
  - The help text says: “Nothing on this page moves or expires while you read it.”
  - Identity codes and pending authenticator confirmation codes do expire after ten minutes.
  - Security requires time-bound codes, so the wording should instead say that the page itself does not rush the user while clearly explaining that security codes have a generous validity period and can be requested again.

## FAILING_ITEMS

- The `otpauth://totp/` provisioning URI does not declare the server’s non-default HMAC-SHA256 and 10-minute OTP parameters. Standard authenticator-app codes generated from the QR code will not match server verification.
- The custom QR encoder incorrectly places one horizontal format-information module at `(8,6)` instead of `(8,7)`, overwriting a timing-pattern module.
- The success screen lacks the required easy-to-find help entry point.
- The help screen incorrectly states that nothing expires while the user reads, despite identity and authenticator setup codes being time-bound.

## NEW_TASKS

1. Make authenticator provisioning and verification interoperable: implement standard RFC 6238-compatible TOTP behavior, preferably HMAC-SHA1 with a 30-second period, or explicitly include matching `algorithm` and `period` parameters in the provisioning URI and verify those exact values server-side.
2. Correct the QR format-information placement in `renderQr` so the horizontal `i === 8` bit is placed at row 8, column 7, while preserving the timing module at row 8, column 6; validate the generated QR with a standards-compliant QR scanner.
3. Add a visible “Need help?” link or equivalent help affordance to the success/recovery-code testing screen.
4. Replace the inaccurate help statement with wording that reassures users there is no reading rush while explaining that codes have a generous validity period and can be resent or regenerated.

## DECISION

FAIL
