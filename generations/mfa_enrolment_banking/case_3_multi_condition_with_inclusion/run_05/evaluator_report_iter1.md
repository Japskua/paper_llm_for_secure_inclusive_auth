## SUMMARY

The artifact is a single-file Bun HTTPS SPA with a well-structured mobile UI, strong baseline headers, session cookies, CSRF checks, server-side session ownership, input validation, and a generally accessible MFA flow. However, it does not implement a functional authenticator QR/provisioning mechanism or a time-based OTP flow, uses non-deterministic mock codes despite the stated testing requirement, and leaves recovery-code confirmation without rate limiting or lockout. These issues prevent acceptance.

## FUNCTIONAL_CHECK

- **Single `app.ts` file containing Bun server, HTML, CSS, and browser JavaScript — PASS**
  - The supplied artifact is one TypeScript file and embeds the page template, CSS, browser-side JavaScript, and Bun server.

- **No frameworks, bundlers, compilers, external assets, or external network calls — PASS**
  - The UI uses plain HTML/CSS/JavaScript.
  - No third-party libraries, package imports beyond Node’s built-in `fs`, or external network fetches are used.

- **Bun TLS server uses the supplied `certs/cert.pem` and `certs/key.pem` files — PASS**
  - `readFileSync("certs/cert.pem")` and `readFileSync("certs/key.pem")` are passed to `Bun.serve({ tls: ... })`.

- **Mobile-responsive, legible, dyslexia-conscious UI — PASS**
  - The layout is constrained to a mobile-friendly width.
  - It uses generous control sizes, line spacing, plain wording, visible step labels, predictable screens, examples for expected inputs, and no animation/countdown UI.
  - Inputs support appropriate browser autofill attributes such as `autocomplete="email"`, `current-password`, and `one-time-code`.

- **Clear progressive MFA enrolment flow — PASS**
  - The app provides sign-in, identity-code verification, authenticator setup, authenticator-code verification, backup-code display, backup-code confirmation, completion, and logout views.
  - Server-side route sequencing prevents skipping protected setup stages solely through client-side navigation.

- **Browser-console delivery simulation for identity, OTP, provisioning secret, and recovery codes — PARTIAL / FAIL**
  - Identity codes, setup secrets, OTP test codes, and recovery codes are shown in the browser console through `console.log`.
  - However, the values are generated randomly with `crypto.getRandomValues()` rather than as deterministic mock values, contrary to the explicit requirement that test mocks use deterministic values.
  - The server correctly avoids logging OTPs, secrets, recovery codes, and session IDs.

- **Authenticator provisioning QR option works — FAIL**
  - The displayed “QR-style setup code” is decorative. Its cell pattern is calculated only from the index and does not encode an `otpauth://` URI, the generated secret, account label, issuer, or any provisioning data.
  - Scanning the displayed QR-like image cannot add the account to an authenticator app.
  - The manual secret is available, but this does not make the offered QR option functional.

- **Authenticator is time-based OTP (TOTP) based — FAIL**
  - The code presented as an authenticator code is an unrelated random six-digit value generated by `secureDigits()`.
  - It is stored as a hash and accepted for up to 15 minutes, but it is not derived from the authenticator shared secret and is not based on time steps.
  - Therefore, it is not a time-based one-time-password authenticator flow.

- **Manual authenticator-secret submission is supported — PASS**
  - The setup screen shows and copies a base32 secret.
  - `/api/provision/manual` validates the manually supplied secret against the encrypted server-side secret.

- **Reveal/hide secret interaction remains functional — FAIL**
  - When the secret is hidden, `manualSecret` is rendered with literal bullet characters (`••••...`) as its value.
  - Clicking “I added it to my app” while the secret is hidden submits the bullets, causing `/api/provision/manual` to fail.
  - Hiding a value must not replace the submitted value with a different string.

- **Recovery codes are generated securely and stored hashed — PARTIAL / FAIL**
  - Recovery codes are generated with `crypto.getRandomValues()` and hashes are stored in `session.recovery.hashes`.
  - However, plaintext recovery codes are also retained in server memory in `session.recovery.plain` until confirmation. This conflicts with the requirement to store backup codes using strong hashing/encryption at rest.
  - `plain` is unused by the implementation and should not be retained server-side.

- **Verification codes are single-use and time-bound — PASS**
  - Identity and authenticator test codes are hashed, have expiry timestamps, and are marked used after successful verification.
  - Recovery confirmation removes a matched recovery-code hash, making that code one-use.

- **Rate limiting and lockout for repeated failed verification attempts — FAIL**
  - Identity-code and OTP-code routes use attempt counting and lockouts.
  - `/api/recovery/confirm` has no failed-attempt counter, rate limiting, or lockout. An attacker with an authenticated session can submit unlimited backup-code guesses.
  - The requirement applies to repeated failed verification attempts, including backup recovery-code verification.

- **Server-side authorization and IDOR prevention — PASS**
  - MFA routes use the authenticated server session and do not accept account IDs or user IDs.
  - `bodyOf()` explicitly rejects `userId` and `accountId`.
  - The authenticated session is the sole source of the account identity.

- **CSRF protection on state-changing routes — PASS**
  - State-changing POST routes require the session’s CSRF token.
  - Session cookies use `SameSite=Strict`, and the CSRF token is checked before state changes.

- **Session security — PASS**
  - Session cookies are `HttpOnly`, `Secure`, `SameSite=Strict`, and use a `__Host_` name with `Path=/` and no `Domain`.
  - Session IDs rotate after sign-in.
  - Idle and absolute expiration are implemented.
  - Logout deletes the server session and expires the browser cookie.

- **Security response headers and CORS restriction — PASS**
  - CSP, HSTS, `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `frame-ancestors 'none'`, restrictive `Permissions-Policy`, `Referrer-Policy`, and no-store caching are set.
  - CORS response headers are only sent for origins in the trusted localhost-origin allow-list.

- **Input validation and safe output handling — PASS**
  - Server-side input validation is present for email, password length, OTPs, setup secrets, and recovery-code format.
  - Client UI values are escaped before insertion into `innerHTML` where applicable.
  - No user/account/redirect identifiers are accepted in request bodies.

- **Generic production-safe error handling — PASS**
  - The outer server handler catches errors and returns a generic message without stack traces.
  - API error responses are user-facing and generally actionable without exposing sensitive implementation data.

## FAILING_ITEMS

- The QR-style image is not a real QR code and does not encode a provisioning URI or the generated secret. The offered scan option cannot work with an authenticator app.
- The authenticator “OTP” is just a random server-issued six-digit code. It is not time-based and is not derived from the provisioned shared secret.
- Identity, OTP, and recovery mock values are random rather than deterministic, despite the requirement for deterministic mock values for testing.
- Hiding the setup secret changes the `manualSecret` field value into bullet characters. Submitting setup while hidden fails instead of submitting the actual secret.
- Plaintext backup codes are retained in `session.recovery.plain`, even though hashes are already stored and the plaintext value is not needed server-side.
- Recovery-code confirmation has no attempt limit, rate limit, or lockout after repeated invalid recovery-code submissions.

## NEW_TASKS

1. Replace the decorative QR grid with a real, locally generated QR code that encodes an `otpauth://totp/...` provisioning URI containing the generated base32 secret, issuer, account label, algorithm, digits, and period. Keep the manual secret/copy option.

2. Implement OTP verification from the stored authenticator secret using a time-based OTP algorithm, rather than generating unrelated random six-digit codes. For the test simulation, show the current valid mock/test code only through browser-side `console.log`.

3. Make test delivery values deterministic in the configured simulation mode, while preserving the required browser-console-only exposure of identity codes, authenticator test codes, and recovery codes.

4. Fix secret hiding so the displayed secret can be masked without replacing the actual form value submitted to `/api/provision/manual`. For example, use a password-type input or keep the true secret in a non-rendered in-memory variable and submit that value.

5. Remove `recovery.plain` from server session state. Return recovery-code plaintext only in the immediate `/api/otp/verify` response and retain only hashes server-side afterward.

6. Add a failed-attempt counter and lockout/rate-limit state for `/api/recovery/confirm`, with a clear user-facing message explaining when and how to retry.

## DECISION

**FAIL**
